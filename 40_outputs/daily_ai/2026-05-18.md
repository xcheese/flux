## 1. Anthropic 将 Agent SDK / `claude -p` 从订阅额度里拆出来：个人自动化要开始算“Agent 预算”

### 来源

- [Claude Help Center：Use the Claude Agent SDK with your Claude plan（updated 2026-05-17）](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan)
- [Claude Code Docs：Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)

### 信号类型

- 成熟度：S2 已确认政策变更
- 来源类型：官方帮助文档 / 官方开发者文档
- 置信度：高

### 一句话结论

从 2026-06-15 起，Claude Agent SDK、`claude -p`、Claude Code GitHub Actions 和通过 Agent SDK 认证的第三方应用，将使用独立的 monthly Agent SDK credit，而不再消耗交互式 Claude 订阅额度。

### 事实 / 观点 / 推断

- 事实：Pro、Max、Team、Enterprise 订阅用户可领取独立 Agent SDK credit；Pro 为 $20，Max 5x 为 $100，Max 20x 为 $200；credit 按用户计，不可团队共享，不滚存。
- 事实：credit 覆盖 Agent SDK、`claude -p` 非交互模式、Claude Code GitHub Actions、通过 Agent SDK 认证的第三方 app；交互式 Claude Code、Claude 网页/桌面/移动端、Claude Cowork 不受影响。
- 观点：Anthropic 正在把“人坐在键盘前使用 Claude”和“程序持续调用 Claude”切成两种经济模型。
- 推断：个人和团队的 Agent 工作流会从“订阅套利”进入“预算管理”阶段，长时间后台自动化、CI 机器人、批量研究脚本都需要重新核算成本。

### 为什么重要

这条会直接影响高频 Claude Code / Codex / Agent SDK 用户。过去很多个人自动化可以隐含地靠订阅额度跑，现在 programmatic usage 会更接近 API 计费逻辑。对市场来说，这是 Agent 产品成熟化的信号：平台开始把自动化负载、交互式使用和生产服务分开定价。对个人来说，下一步不是只问“能不能自动跑”，而是要问“它每月会烧多少钱、值不值得、什么时候该停”。

### 对我的启发

你的知识库自动化、`ai-news`、视频分析、代码代理、后台采集都需要一套 Agent 预算账本。每个自动化流程要记录触发频率、模型、token、外部 API、是否无人值守、失败重跑次数和最终产出，否则很快会看不清真实收益。

### 待验证点

- 具体扣费体验、credit claim 流程、超额暂停行为要等 2026-06-15 后实测。
- 第三方工具是否能顺利通过 Agent SDK 认证，以及哪些工具会转向 API key 模式。
- 对 Team/Enterprise 来说，per-user credit 不可共享可能会迫使团队更早迁移到 Claude Platform API key。

### 可行动作

- 建一个 `agent_budget_ledger.md`：流程名、触发频率、预计 token、是否无人值守、每次产出、每月预算上限。
- 把所有使用 `claude -p`、GitHub Actions、Agent SDK 的脚本列出来，标记 2026-06-15 后会进入哪个计费池。
- 给自动化流程设一个硬规则：超过预算或连续失败 2 次就停止，并写入日志等待人工确认。

## 2. NVIDIA SANA-WM：开源世界模型开始把“一分钟 720p 可控视频”压到单 GPU 级别

### 来源

- [arXiv：SANA-WM: Efficient Minute-Scale World Modeling with Hybrid Linear Diffusion Transformer（2605.15178）](https://arxiv.org/abs/2605.15178)
- [Hugging Face Papers：SANA-WM](https://huggingface.co/papers/2605.15178)
- [GitHub：NVlabs/Sana](https://github.com/NVlabs/Sana)

### 信号类型

- 成熟度：S1/S2 论文 + 项目页 + 开源代码路径，外部复现仍待观察
- 来源类型：论文、Hugging Face paper page、NVIDIA NVLabs GitHub repo
- 置信度：中高

### 一句话结论

NVIDIA NVLabs 发布 SANA-WM，一个 2.6B 参数开源 world model，可从单张图和 6-DoF camera trajectory 生成 60 秒 720p 视频，论文称蒸馏版可在单张 RTX 5090 上用 34 秒完成 60 秒片段 denoise。

### 事实 / 观点 / 推断

- 事实：SANA-WM 使用 Hybrid Linear Diffusion Transformer、Dual-Branch Camera Control、Two-Stage Generation Pipeline 和 camera pose annotation pipeline。
- 事实：论文称训练使用约 213K public video clips、64 张 H100 训练 15 天；60 秒视频可在单 GPU 上生成；相较 prior open-source baselines 有更强 action-following，并达到约 36x throughput。
- 观点：这不是普通文生视频更新，而是“可控 camera trajectory + 长时一致性 + 推理效率”的组合推进。
- 推断：开源视频生成的竞争重点会从单段短视频质量，转向可控世界建模、长时一致性、可本地/低成本运行和可集成到游戏/仿真/内容生产流程。

### 为什么重要

世界模型是 AI 视频、游戏生成、机器人仿真、自动驾驶数据、虚拟拍摄的重要基础层。SANA-WM 的关键不是“又能生成视频”，而是把分钟级、720p、camera-controlled video 的成本和硬件门槛明显压低。如果复现成立，个人和小团队会更容易做可控镜头、空间一致的视频实验，而不完全依赖闭源 API。

### 对我的启发

你的 AI 学习不应只跟踪文本模型和 coding agent，也要开始跟踪“可控生成 + 世界建模”的工具链。未来内容生产和产品原型可能不是写 prompt 生成片段，而是设定初始画面、相机路径、场景约束和后续编辑 pipeline。

### 待验证点

- “open-source”具体包括哪些权重、训练代码、推理脚本和许可证限制，需要逐项检查。
- 单 RTX 5090 的 34 秒推理数据需要社区复测，尤其是显存、量化质量、失败率和长视频一致性。
- 生成结果是否真的具备可用的物理/空间一致性，还是主要在视觉连续性上表现好。

### 可行动作

- 建一张 `open_world_model_watchlist.md`，记录 SANA-WM、Sora/Runway/Kling 类闭源工具、开源 video diffusion 的能力边界。
- 阅读 SANA-WM 的 four core designs，整理成“长视频生成为什么难”的 5 条笔记。
- 观察 Hugging Face / ComfyUI / Diffusers 社区是否出现可运行 demo，再决定是否本地尝试。

## 3. Microsoft MDASH：安全领域的 Agent 价值开始从“回答问题”转向“发现、争辩、证明漏洞”

### 来源

- [Microsoft Security Blog：Defense at AI speed: Microsoft’s new multi-model agentic security system tops leading industry benchmark（2026-05-12）](https://www.microsoft.com/en-us/security/blog/2026/05/12/defense-at-ai-speed-microsofts-new-multi-model-agentic-security-system-tops-leading-industry-benchmark/)

### 信号类型

- 成熟度：S2 官方生产系统披露；部分能力在 private preview
- 来源类型：Microsoft Security 官方技术博客
- 置信度：中高

### 一句话结论

Microsoft 披露 MDASH，一个 multi-model agentic scanning harness，编排 100+ specialized agents，用于发现、辩论、验证和证明漏洞；官方称其帮助找到 16 个 Windows networking/authentication 漏洞，并在 CyberGym 上达到 88.45%。

### 事实 / 观点 / 推断

- 事实：MDASH 将流程拆成 Prepare、Scan、Validate、Dedup、Prove 等阶段，并使用 auditor、debater、prover 等不同 agent 角色。
- 事实：Microsoft 称该系统在私有 StorageDrive 测试中找到 21/21 planted vulnerabilities 且 0 false positives；在 `clfs.sys` 五年 MSRC case 上 96% recall，在 `tcpip.sys` 上 100% recall。
- 观点：安全 Agent 的价值不只是“模型会不会看代码”，而是多模型、多角色、可证明、可落地到 Patch Tuesday 的工程系统。
- 推断：高价值 Agent 产品会越来越像“带领域插件和验证阶段的流水线”，而不是一个通用聊天机器人加工具列表。

### 为什么重要

这条对 Agent 设计很有启发。Microsoft 明确说 “the system is the product”：模型只是输入之一，真正的护城河在攻击面建模、候选发现、交叉辩论、动态证明、领域插件和已有安全流程的集成。这和个人知识库/代码代理也一致：如果没有结构化流程和验证环节，强模型也很容易产出漂亮但不可用的结论。

### 对我的启发

你可以把 MDASH 的模式迁移到个人工作流：一个 Agent 不要直接给最终答案，而是分成 `prepare -> scan -> debate -> prove -> write`。例如 AI news 可以先抓候选，再反向质疑，再验证来源，再写摘要；代码审查可以先找风险，再让另一个角色反驳，再只保留可证明问题。

### 待验证点

- MDASH 的公开数字来自 Microsoft 自有代码和内部流程，外部团队是否能复现类似收益仍不确定。
- 该系统不等于单个可下载模型，很多价值来自 Microsoft 的代码库、MSRC 数据、领域插件和安全工程流程。
- 公开 CyberGym 分数能说明一部分能力，但不能完全代表真实生产漏洞发现的召回率和误报成本。

### 可行动作

- 把 `ai-news` 下一步改进为两阶段：先写候选池和淘汰理由，再写最终 3 条，保留可复盘记录。
- 为代码审查建立一个 `debate` 模板：发现者列风险，反驳者要求证据，最终只输出能定位到文件/行/触发条件的问题。
- 做一个小型 `prove` 实验：任何 Agent 给出的行动建议，都要求附上来源、可执行验证步骤和失败条件。
